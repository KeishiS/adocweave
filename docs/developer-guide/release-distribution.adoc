= 配布仕様

この文書は、配布物と安全上の保証の正本です。利用者の導入、更新、checksumおよび
attestationの確認はxref:../user-guide/release-installation.adoc[インストールと更新]、開発者がReleaseを
準備する手順はxref:../../CONTRIBUTING.adoc[コントリビューションガイド]を参照してください。

成果物名、対象環境および個数はcargo-distの設定からplanへ導出します。独自の配布計画や配布manifestを
別の正本として保守しません。公開処理はplanにない成果物や処理を追加せず、構築後は標準dist-manifestと
実際のファイルを照合します。

[#distribution-boundary]
== 配布単位

ネイティブ実行ファイルは、一つのcommit、一つの``vX.Y.Z``タグおよび一つのGitHub Releaseを公開単位とします。
WebAssemblyパッケージとtextlint用Processorは独立した版を持ち、それぞれ``wasm/vX.Y.Z``タグと
``textlint-plugin-asciidoc/vX.Y.Z``タグからnpm Registryへ直接公開します。
Zed拡張も独立した版を持ち、公式Zed拡張レジストリが``editors/zed``のソースを構築して配布します。
いずれも同じバージョン番号を別の内容へ再利用しません。

cargo-distは、OSとCPU architectureごとの``adocweave-<target>.zip``をnative成果物として構築します。
VS Code拡張は追加成果物として同じplanとGitHub Releaseへ含めます。
GitHubが自動生成するsource archiveは検証対象の成果物に含めません。

registryへも公開する追加成果物は、GitHub Releaseへ添付して検証したものと同じ内容を送ります。VS Code拡張は
Open VSX RegistryとVisual Studio Marketplaceへ公開します。registry向けに構築し直しません。
WebAssemblyパッケージとtextlint用Processorは、それぞれの
専用workflowで一度だけ構築して検査し、その成果物をnpm Registryへ送ります。
Rust crateはcrates.ioへ公開しません。

Visual Studio Marketplaceは公開後のVSIXへ署名情報を追加するため、取得したVSIX archive全体のbyte列は送信元と
異なる場合があります。公開後の検査では拡張ID、version、target、署名以外のfile一覧および各fileの内容を照合し、
Marketplaceが追加したZIP内の標準署名領域（``_xmlsignatures/``と対応するmetadata）だけを比較から除きます。

外部サービスへの送信はGitHub Releaseの公開後に、公開先ごとの再利用workflowで行います。Release workflowは
3つのworkflowへ同じstable tagと完全なcommit SHAを渡し、直接かつ並列に呼び出します。独自eventと手動起動用の
入口は使用しません。一つの送信が失敗しても別の公開先を差し戻さず、Release workflowの``Re-run failed jobs``で
失敗した送信だけを同じtagとcommitに対して再実行します。
この公開単位を選んだ理由はxref:adr/0043-independent-distribution-units.adoc[ADR 0043]、公開先と
権限の分離はxref:adr/0023-publication-boundary.adoc[ADR 0023]を参照してください。

[#artifact-contracts]
== 成果物の保証

native archiveは対象OSのnative runnerで構築し、``adocweave``実行ファイル、license、READMEおよび
第三者依存の通知を収録します。Language Server用の別の実行ファイルは収録せず、``adocweave lsp``で起動します。
構築対象のarchitecture、link方式、最小OS版、実行権限、CLIの基本操作およびLanguage Serverのstdio lifecycleを
実際の成果物で確認します。

native実行ファイルへOS code signingは行いません。Artifact Attestationは構築元を示しますが、OS code signingの
代替ではありません。利用者に表示されるOS警告と確認方法は利用者向け文書に記載します。

WebAssembly packageは公開client、Web WorkerおよびWebAssemblyを一組として配布します。公開APIと内容は
xref:core-profile.adoc#wasm-api[WebAssembly API]を基準とし、Worker内部のmessage形式は公開互換仕様に
含めません。完成archiveをcross-origin isolationのない静的配信とbundlerの両方で実行し、size上限も
成果物検査で確認します。

ブラウザー向けの入口はWeb Workerで実行し、取消しとWASM trapの分離を提供します。Node.js向けの入口は
同じprocessで同期的に実行します。どちらも共通の要求と応答の形式を使用し、利用側がpackage内部の配置へ
直接依存しない公開入口を提供します。

VS Code拡張とZed拡張はLanguage Serverを同梱しません。設定で指定した絶対path、``PATH``、自動取得の順で
``adocweave``を選び、``lsp``引数を付けて起動します。Zed拡張は最新の安定版GitHub Releaseにある
``adocweave-<target>.zip``を使用し、拡張版との一致を求めません。現在の選択規則と手動導入方法は利用者向け文書を基準とし、
この分担の理由はxref:adr/0028-editor-language-server-boundary.adoc[ADR 0028]を参照してください。

textlint用ProcessorはProcessor、TxtAST変換、型定義、Node.js向けWebAssembly、licenseおよび第三者依存の通知を
同じarchiveへ収録します。install時のscript、実行時npm依存、``node_modules``、source mapおよび機械固有pathを
収録せず、実行時に追加downloadしません。includeと自動修正は公開範囲に含めません。公開interfaceと利用法は
link:../../packages/textlint-plugin-asciidoc/README.md[packageのREADME]を基準とします。

第三者依存の通知はlockfileから生成し、成果物へ到達するpackageの名前、versionおよびSPDX licenseを記録します。
license情報のないpackageは受理しません。SBOMを公開しない判断は
xref:adr/0036-no-unconsumed-sbom.adoc[ADR 0036]を参照してください。

[#distribution-integrity]
== 完全性と来歴

cargo-distのplanは、workspaceのバージョン、``vX.Y.Z``タグ、native成果物、ネイティブ版の追加成果物および実行jobを確定します。
各構築jobが出力する標準dist-manifestを集約し、公開時に最終的な標準dist-manifestを生成します。planまたは
dist-manifestにないfile、欠落したfile、異なるバージョンおよび異なるsource commitを受理しません。

``sha256.sum``は同じGitHub Releaseに含める成果物の共通checksum一覧です。cargo-distがnative archiveごとに
生成する``.sha256``も公開します。外部サービスへ送る成果物は、共通checksumと照合してから使用します。

GitHub Releaseへ添付する成果物、checksumおよび標準dist-manifestにはGitHub Artifact Attestationを付けます。
credentialや署名fileはarchiveへ埋め込みません。privateリポジトリから取得する場合も、利用者が明示的に与えた
GitHub認証だけを使用し、credentialをmanifest、log、sourceまたは設定例へ記録しません。

[#publication-permissions]
== 公開に使用する権限

planの生成、構築および成果物検査はrepositoryの読取り権限だけで実行し、公開先のsecretを参照しません。
GitHub Releaseへ添付する``host`` jobだけが、``github-release`` environmentでReleaseへの書込みとArtifact Attestationに
必要なOIDC権限を持ちます。
Release作成後は、公開先ごとの再利用workflowを最小権限で直接呼び出します。公開先の資格情報は各workflowの
公開jobへ設定したGitHub environmentだけから取得し、呼出し元のjobへ渡しません。外部actionは完全なcommit SHAへ
固定します。

Open VSX Registryへの公開workflowの``publish`` jobだけが専用tokenを使用します。Visual Studio MarketplaceはTrusted Publisherと
``vsce publish --oidc``を使用し、長期tokenを持ちません。MarketplaceのTrusted Publisherにはrepository、
呼出し元workflow file``release.yml``および``marketplace-publish`` environmentを登録します。OIDCのworkflow identityは
再利用workflowの``marketplace-publish.yml``ではなく``release.yml``です。両workflowともGitHub Releaseから取得した
VSIXのchecksumとattestationを確認し、別の成果物を公開しません。

textlint用Processorでは、``textlint-plugin-publish.yml``の公開jobだけがGitHub environment``npm-publish``で
``id-token``の書込みを持ちます。Trusted Publisherへ登録するworkflow identityは
``textlint-plugin-publish.yml``、Environment名は``npm-publish``です。workflowは
``textlint-plugin-asciidoc/vX.Y.Z``タグ、パッケージの版、commitおよび``main``への統合を照合してから
構築済みの成果物を送信します。公開後はnpmから導入し直し、署名、provenance、固定した利用側および
``npx``での動作を確認します。

WebAssemblyパッケージでは、``wasm-publish.yml``の公開jobだけがGitHub environment``npm-publish``で
``id-token``の書込みを持ちます。Trusted Publisherへ登録するworkflow identityは``wasm-publish.yml``、
Environment名は``npm-publish``です。workflowは
``wasm/vX.Y.Z``タグ、``packages/wasm/package.json``の版、commitおよび``main``への統合を照合してから
構築済みの成果物を送信します。公開後はnpmから導入し直し、``npm audit signatures``で署名とprovenanceを検証して、
Node.jsと実ブラウザーで同じパッケージを確認します。

stable Releaseの公開後に、Cachix用workflowの公開jobだけが``CACHIX_AUTH_TOKEN``を使用します。公開jobは
公開済みのtag、commitおよびworkspace版を照合し、同じcommitから``x86_64-linux``と``aarch64-linux``向けに
構築したNix packageと依存物一式をCachixへ送信します。

送信後は、書込みtokenを持たない別のrunnerがローカルでの構築を禁止し、Cachixだけから対象packageを取得します。
取得した``adocweave``のversionと``adocweave lsp``の起動を確認します。Nix store pathは内容から決まるため、
同じtagでworkflowを再実行しても既存の内容は変わりません。

最初の自動公開より前に、``github-release``、``binary-cache-publish``、``marketplace-publish``、``npm-publish``および
``open-vsx-publish``の各environmentを作成します。``npm-publish``は``wasm/v*``と
``textlint-plugin-asciidoc/v*``を許可し、ほかの
environmentはRelease workflowを起動する``v*``だけを許可します。CachixとOpen VSXのtokenはrepository全体ではなく対応するenvironmentへ置き、
MarketplaceのTrusted Publisherには``release.yml``、npmパッケージのTrusted Publisherにはそれぞれ
``wasm-publish.yml``と``textlint-plugin-publish.yml``を登録し、前述のEnvironment名と対応させます。

repositoryへの書込み権限がある利用者による手元からのtag作成を、workflowだけで機械的に禁止することはできません。
tag rulesetを追加せず、公開前検査によって権限を制限する理由は
xref:adr/0023-publication-boundary.adoc#publication-authority[ADR 0023]を参照してください。

[#publication-failure]
== 公開と失敗時保証

公開前検査に成功した``main``のcommitへ``vX.Y.Z``タグを作成すると、cargo-distのRelease workflowが起動します。
共通のrelease contractは、checkout時に``origin/main``を含む履歴を取得し、tag、commitおよびworkspace版の対応と、
tagのcommitが``main``に含まれることを``host``より前に一度だけ検査します。workflowはplanを生成し、native成果物と
追加成果物を構築して検査した後、一つのGitHub Releaseへ公開します。
異なるworkflow runや手元の成果物を途中で混在させません。Release作成に成功すると、Release workflow内の3つのjobが
公開先ごとの``workflow_call``専用workflowを直接かつ並列に呼び出します。呼出し先へはplanで確定したtagと
Releaseを作成した完全なcommit SHAだけを渡します。各公開jobはstableなRelease、tagのcommit、checkoutしたcommit、
workspace版、checksumおよびattestationを照合します。``main``との関係は共通のrelease contractを正本とし、公開先ごとの
workflowでは重ねて検査しません。npmパッケージはこのRelease workflowへ含めません。

``main``の検査に成功したcommitへ``wasm/vX.Y.Z``または``textlint-plugin-asciidoc/vX.Y.Z``タグを作成すると、
対応するパッケージ専用workflowが起動します。workflowはタグ、パッケージの版、commitおよび``main``への統合を
確認し、候補を構築してパッケージに対応する利用側で検査します。検査した同じ成果物をnpmへ公開し、npm上の内容、
署名およびprovenanceを確認します。
失敗した場合は同じworkflow runの失敗jobだけを再実行します。公開済みの同じ版は内容を確認して送信を省略し、
成果物の修正が必要な場合は新しい版とタグを使用します。

外部公開jobはRelease workflowの一部であり、いずれかが失敗するとRelease workflow全体も失敗します。外部サービスへの
送信だけが失敗した場合は、GitHub Actionsの標準操作``Re-run failed jobs``を使用します。成功済みのRelease作成jobと
公開jobはそのままにし、失敗した再利用workflowと後続jobだけを再実行します。公開workflowはtag単位のconcurrencyと、
公開済み内容を検証して送信を省略する処理を持つため、同じtagとcommitで繰り返しても公開済みの内容を変更しません。

一度作成したstable tagとReleaseは削除、置換または自動的な差戻しを行いません。GitHub Releaseの公開前に
一時的な原因でworkflowが失敗した場合は、同じtagとcommitに対して再実行します。sourceの修正が必要な場合と、
公開後の確認で問題が見つかった場合は、新しいcommitとバージョンを使用します。tag、commitおよび一回の公開処理を
対応付ける理由は
xref:adr/0032-same-run-release-publication.adoc[ADR 0032]を参照してください。

外部サービスへの送信だけが失敗した場合は、GitHub Releaseを作り直しません。``Re-run failed jobs``で同じ成果物の
送信だけをやり直します。npmは公開済みversionを上書きしません。npmで問題が見つかった場合は
``deprecate``で警告を表示し、修正は新しいversionで行います。``unpublish``は安全上必要な場合に限ります。
一度``unpublish``したversion番号は再利用しません。

[#distribution-verification]
== 段階ごとの検証

Pull Requestではsource、試験、生成fileおよび文書を標準の``verify``で検査します。cargo-distは``dist plan``を
実行して、workspace版、成果物およびjobの構成を検査しますが、配布成果物は構築しません。

``main``ではcross target、fuzz、Nix packageなどの統合検査を行います。ネイティブ版のRelease workflowでは固定したtagとcommitに
対してplanを再生成し、対象OSでnative成果物を構築します。ネイティブ版の追加成果物は専用の構築処理で作成し、cargo-distの
標準dist-manifestへ統合します。完成成果物は対象OSまたはエディタで検査します。WebAssemblyパッケージと
textlint用Processorは、それぞれの公開workflowで候補を構築し、公開前後に対応する利用側で検査します。

taskの現在の入口とReleaseの操作手順はxref:../../CONTRIBUTING.adoc[コントリビューションガイド]を基準とします。
検査をこの段階へ分ける理由はxref:adr/0031-path-independent-pull-request-gate.adoc[ADR 0031]、task間の責務は
xref:adr/0033-make-task-boundary.adoc[ADR 0033]を参照してください。

GitHub Releaseの公開後は、成果物を実際のRelease URLから取得してchecksumとattestationを確認します。
WebAssemblyパッケージとtextlint用Processorはnpm Registryから取得して確認します。
外部registryへ公開したpackageと拡張はregistryから導入し直し、署名などregistry固有のmetadataを除く内容、
基本操作および固定consumerでの動作を確認します。これらの確認は公開済みの成果物に対して行い、公開前の検査と
役割を分けます。
