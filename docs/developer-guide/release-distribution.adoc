この文書は、GitHub Releaseへ公開する成果物と安全上の保証の正本です。利用者の導入、更新、checksumおよび
attestationの確認はxref:../user-guide/release-installation.adoc[インストールと更新]、開発者がreleaseを
準備して公開する手順はxref:../../CONTRIBUTING.adoc[コントリビューションガイド]を参照してください。

[#distribution-boundary]
== 製品ごとの配布単位

配布計画に記載した各製品は、独立したversion、tagおよびGitHub Releaseを持ちます。一つのReleaseには一製品の
成果物だけを公開します。変更していない製品の成果物を別のReleaseへコピーせず、同じ製品versionを再発行しません。
GitHubが自動生成するsource archiveは検証対象の成果物に含めません。

registryへも公開する製品では、GitHub Releaseへ添付した成果物と同じbyte列を送り、registry向けに
構築し直しません。現在registryへ公開する製品はVS Code拡張、WebAssembly packageおよびtextlint用
Processorです。VS Code拡張はOpen VSX RegistryとVisual Studio Marketplaceの両方へ、残る2つは
npm Registryへ公開します。CLIとZed拡張はGitHub Releaseからの導入だけを対象とします。
Rust crateはcrates.ioへ公開しません。

VS Code拡張は2つのregistryへ同じVSIXを送ります。どちらか一方の送信が失敗しても、もう一方を
止めません。両方ともGitHub Releaseの公開後に独立したworkflowで行い、同じtagを指定して単独で
再実行できます。

npmへの公開はGitHub Releaseの公開後に別のworkflowで行い、送信後にregistryが記録したintegrityが
Releaseの成果物と一致することを確認します。続けて、公開したpackageをregistryから導入し直し、
clean installと``npx``の経路を観測します。

公開には配布計画の``tagPrefix``に従うstable tagを使用します。tag、source commit、versionの正本、
配布manifestおよび成果物が一致しない場合は公開しません。

この公開単位を選んだ理由はxref:adr/0027-product-release-trains.adoc[ADR 0027]、公開先と権限の分離は
xref:adr/0023-publication-boundary.adoc[ADR 0023]を参照してください。

[#artifact-contracts]
== 成果物の保証

NativeのCLIとLanguage Serverは別のarchiveとして、対象OSのnative runnerで構築します。archive layout、
実行file、licenseおよび第三者依存の通知は配布計画と成果物検査を基準とします。構築対象のarchitecture、
link方式、最小OS版、実行権限およびstdio lifecycleを実際の成果物で確認します。

Native binaryへOS code signingは行いません。Artifact Attestationは構築元を示しますが、OS code signingの
代替ではありません。利用者に表示されるOS警告と確認方法は利用者向け文書に記載します。

WebAssembly packageは公開client、Web WorkerおよびWebAssemblyを一組として配布します。公開APIと内容は
xref:core-profile.adoc#wasm-api[WebAssembly API]を基準とし、Worker内部のmessage形式は公開互換仕様に
含めません。完成archiveをcross-origin isolationのない静的配信とbundlerの両方で実行し、size上限も
成果物検査で確認します。

入口は二つあります。ブラウザー向けの入口はWeb Workerで実行し、取消しとWASM trapの分離を提供します。
ビルド時向けの入口は同じprocessで同期的に実行し、どちらも提供しません。要求と応答の形式は共通です。
静的サイト生成のようにNodeで実行する利用側が、packageの内部layoutへ直接触れずに済むよう用意します。

VS Code拡張とZed拡張はLanguage Serverを同梱せず、download、cacheまたは更新を実装しません。現在の導入方法と
実行fileの選択規則は利用者向け文書を基準とします。この分担の理由は
xref:adr/0028-editor-language-server-boundary.adoc[ADR 0028]を参照してください。

textlint用ProcessorはProcessor、TxtAST変換、型定義、Node.js向けWebAssembly、licenseおよび第三者依存の通知を
同じarchiveへ収録します。install時のscript、実行時npm依存、``node_modules``、source mapおよび機械固有pathを
収録せず、実行時に追加downloadしません。includeと自動修正は公開範囲に含めません。公開interfaceと利用法は
link:../../packages/textlint-plugin-asciidoc/README.md[packageのREADME]を基準とします。

第三者依存の通知はlockfileから生成し、成果物へ到達するpackageの名前、versionおよびSPDX licenseを記録します。
license情報のないpackageは受理しません。SBOMを公開しない判断は
xref:adr/0036-no-unconsumed-sbom.adoc[ADR 0036]を参照してください。

[#distribution-integrity]
== 完全性と来歴

配布manifestは製品、version、source commitおよび公開成果物を記録します。checksum一覧は公開成果物と
配布manifestを対象とします。candidateディレクトリに未知のfile、subdirectory、欠落、改変または異なる
source commitがある場合は受理しません。

公開する成果物、配布manifestおよびchecksum一覧にはGitHub Artifact Attestationを付けます。credentialや
署名fileはarchiveへ埋め込みません。privateリポジトリから取得する場合も、利用者が明示的に与えたGitHub認証だけを
使用し、credentialをmanifest、log、sourceまたは設定例へ記録しません。

[#publication-permissions]
== 公開に使用する権限

計画、構築、成果物検査およびcandidate集約はread-onlyで実行し、repository secretを参照しません。
GitHub Releaseへの書込みとOIDCは、保護した``github-release`` Environmentを使用する公開jobだけへ付与します。
公開jobは承認後にもsource commit、candidate、checksumおよび成果物集合を再検査します。外部actionは完全な
commit SHAへ固定します。

Open VSXへ公開する場合だけ、専用workflowが最小権限のtokenを使用します。このworkflowはGitHub Releaseから
取得したVSIXのchecksumとattestationを確認し、別の成果物を公開しません。

npmへ公開する場合だけ、専用workflowが``id-token``の書込みを受け取ります。npmのTrusted Publishingは
長期tokenの代わりにOIDCで公開元を確認するため、このworkflowはregistry用のsecretを参照しません。
repositoryに対する権限はread-onlyで、GitHub Releaseから取得したarchiveのchecksumとattestationを確認して
から送信します。送信後は、registryが記録したintegrityがReleaseの成果物と一致することを確かめます。

CLIのstable Releaseを公開した場合だけ、専用workflowが``CACHIX_AUTH_TOKEN``を使用します。workflowは公開済みの
tagとcommit、成果物のchecksumおよびattestationを再検査し、同じcommitから構築したNix package closureだけを
Cachixへ送信します。repositoryに対する権限はread-onlyで、ほかのjobはこのtokenを参照しません。

repositoryへの書込み権限がある利用者による手元からのtag作成を、workflowだけで機械的に禁止することはできません。
tag rulesetを追加せず、Environmentと公開前検査によって権限を制限する理由は
xref:adr/0023-publication-boundary.adoc#publication-authority[ADR 0023]を参照してください。

[#publication-failure]
== 公開と失敗時保証

公開は、固定した``main``のcommitから一つのworkflow runでcandidateを一度だけ構築し、その同じ成果物を検査、承認、
attestationおよび公開へ渡します。tagより前の失敗ではtagとReleaseを作りません。公開途中の失敗では、そのrunが
作成した非公開状態だけを識別して片付け、他のrunや利用者が作った状態を変更しません。

一度公開したstable Releaseは自動で差し戻しません。公開後の確認で問題が見つかった場合は新しいversionで修正します。
同一runで公開する理由と状態の所有方法はxref:adr/0032-same-run-release-publication.adoc[ADR 0032]を参照してください。

registryへの送信だけが失敗した場合、GitHub Releaseは公開済みのため作り直しません。同じtagを指定して該当の
公開workflowを実行し、同じ成果物の送信だけをやり直します。npmは公開済みversionの上書きを拒否するため、
再実行しても公開済みの版は変わりません。npmで問題が見つかった場合は``deprecate``で警告を表示し、修正は
新しいversionで行います。``unpublish``は安全上必要な場合に限ります。一度``unpublish``したversion番号は
再利用できません。

[#distribution-verification]
== 段階ごとの検証

Pull Requestではsource、試験、生成fileおよび文書を標準の``verify``で検査し、配布candidateは構築しません。
``main``ではcross target、fuzz、Nix packageなどの統合検査を行います。公開workflowではこれらを固定commitに対して
再確認し、選択した製品の完成成果物を対象OS、Browserまたは固定consumerで検査します。

taskの現在の入口とreleaseの操作手順はxref:../../CONTRIBUTING.adoc[コントリビューションガイド]を基準とします。
検査をこの段階へ分ける理由はxref:adr/0031-path-independent-pull-request-gate.adoc[ADR 0031]、
task間の責務はxref:adr/0033-make-task-boundary.adoc[ADR 0033]を参照してください。

textlint用Processorは公開後に実際のRelease URLから取得し、公開checksumとの一致と``npx``による単発実行を
確認します。npmへの公開後は、registryのversion解決を経た導入も同じように確認します。これらの確認は
公開済みの成果物に対してだけ行い、公開前の検査と重複させません。
