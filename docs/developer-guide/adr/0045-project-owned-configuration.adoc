= ADR 0045: プロジェクト設定をプロジェクト処理へ統合
:status: accepted

== 状態

採用

== 背景

``adocweave-project``は、設定の探索と読込、利用者による上書き、ファイル読込権限および処理上限を
一つの要求として処理します。一方、設定値の型、TOMLの解釈、既定値およびスキーマ生成は
``adocweave-config``に分かれていました。この分割により、設定の読込結果を別crateの型から
``adocweave-project``の型へ包み直し、同じ上限を用途別の型へ変換する必要がありました。

設定ファイルの取得には、文書と関連ファイルに使う``ProjectAuthority``と同じ権限が必要です。
設定だけを扱う独立した探索APIを残すと、権限の決定と取得結果の固定を別の経路でも実装することになります。

== 決定

設定値の型、TOMLの解釈、既定値、相対パスの解決およびJSON Schema生成を``adocweave-project``が
所有します。``ProjectConfig``を処理に用いる設定値そのものとし、別の解決済み設定型では包みません。
設定の選択は``ProjectConfigSelection``、要求単位の上書きは``ProjectConfigOverrides``で表します。

設定の探索と読込は``ProjectAuthority``を持つプロジェクト処理だけが行います。読込結果は要求内で固定し、
設定専用の探索API、読込APIおよび呼出側から解決済み設定を注入する選択肢は提供しません。

ファイル数、合計容量および一ファイルの容量は``ProjectResourceLimits``で表します。設定に由来する上限と
要求全体の上限で同じ型を使います。ファイルの取得と使用量の計測も``adocweave-project``内で行い、
別の層の上限型へ変換しません。
``adocweave-config``クレートは削除します。

ADR 0011の厳格な設定形式、権限を設定から拡張しない原則および設定の優先順位は維持します。
ADR 0037のRust型からスキーマを生成する方針も維持し、その正本を``adocweave-project``へ移します。

== 検討した代替案

**独立crateを維持する。** 設定値を複数の処理系で再利用できますが、公式のCLIとLanguage Serverは
どちらもプロジェクト処理を経由します。現在は独立した利用者がなく、型の変換と読込経路だけが増えるため
採用しません。

**設定取得用の汎用ファイルシステム抽象を追加する。** 埋込み先が取得方法を差し替えられますが、
既存の``ProjectAuthority``と同じ権限管理を別の仕組みでも表すことになります。必要な取得方法は
開いている文書の内容と権限内のローカルファイルで表せるため採用しません。

== 結果

設定の構造、既定値、検証、取得および適用が一つのプロジェクト処理にまとまります。CLIとLanguage Serverは
設定の選択と上書きだけを要求へ渡し、設定専用crateへ依存しません。

Rust APIの利用者は、解決済み設定を直接注入できません。設定ファイルを探索するか明示的に指定する場合は
``ProjectConfigSelection``を使い、組込み既定値だけを使う場合は``Disabled``を指定します。
