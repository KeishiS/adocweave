= ADR 0021: 3製品で共通の開発手順と公開仕様

:status: superseded by ADR 0023

決定の正本はxref:0023-publication-boundary.adoc[ADR 0023: 公開と配布の境界]です。
この文書は当時の文脈と判断の経緯を残します。

== 文脈

AdocWeaveは、同じ開発者が並行して開発するMarginalisとRenkanから利用されます。3つのrepositoryは
それぞれ独立したCIと公開workflowを持ち、task名、Release Notesの書き方、release manifestの形、
ブランチやmergeの規約が少しずつ違っていました。個人開発では、repositoryを行き来するたびに手順を
思い出す負担が、repositoryの数だけ積み上がります。

一方で、AdocWeaveの公開物はnative archive、browser package、editor拡張、textlint用パッケージと多く、
target別のbuild、smoke test、installation E2E、SBOM、checksum、attestationをAdocWeave固有の検査として
持っています。これらを他の2製品へ合わせて削ることはできません。

== 決定

外から見える手順と公開仕様だけを3製品で共通にし、検査の中身と書き込み権限を持つworkflowは各repositoryに
残します。

* 公開方式は、``main``の検証済みcommitをそのままtagとGitHub Releaseへ昇格するbuild-once／promote方式の
  ままとします。
* ``release-manifest.json``は共通schema（``schemaVersion`` 1）に従い、``product``、``packageVersion``、
  ``rustVersion``、``nodeVersion``、``releaseNotes``、``assets``を必須項目とします。共通の``assets``は
  repository内のfileをそのまま公開する一覧です。AdocWeaveの成果物はbuildで作るため``assets``は空とし、
  target、archive、SBOMおよびchecksumは拡張項目``distributionPlan``が指す``release/distribution-plan.json``が
  決めます。AdocWeave固有のschema version（従来の4）は廃止します。
* Release Notesのうち人が書く部分は``release/notes.md``へ置きます。題名は``# AdocWeave vX.Y.Z``、
  見出しは``## 主な変更``、``## 対応環境``、``## 公開契約と破壊的変更``、``## vX.Y.Zへの移行``、
  ``## 更新とロールバック``、``## 既知の制約``、``## 配布物の検証``をこの順に一度ずつ置き、
  各節に本文を書きます。``tools/release-notes.mjs``はこの形を検査し、正本のfileから決まる部分
  （配布target、公開仕様のversion、Rust APIの破壊的変更と移行、textlintの対応範囲）を各節の後ろへ追記します。
  公開仕様について「変更していません」と述べる主張は、従来どおり``tools/release-claims.mjs``がbaseline tagとの
  差分で照合します。
* ``cargo make``の外向きtask名は``fmt``、``fmt-check``、``verify``、``security-audit``、``acceptance``、
  ``release-check``とし、既定taskは``verify``です。AdocWeaveでは``security-audit``が
  ``dependency-governance``を、``acceptance``が``verify-with-global-candidate``とhost向けのnative smoke、
  installation E2Eを指します。
* Pull Requestの必須checkは``verify``の一つだけとし、source quality、dependency governance、fuzz、
  Nixパッケージ、公開Rust API差分、および変更に応じて選択したcandidate build、smoke test、
  installation E2Eの結果を``always()``で集約します。
* 作業規約は、remote名``upstream``、ブランチ名``agent/<種別>/<目的>``（人の作業は``<種別>/<目的>``）、
  ``main``追従はrebaseではなく``upstream/main``のmerge、統合はsquash方式のauto-mergeとします。
* workflowの権限境界は、外部actionの完全なcommit SHA固定、jobごとの``timeout-minutes``、
  Pull Requestとmain pushのread-only権限、repository secretの不参照を共通の前提とします。
  書き込み権限を持つ公開workflowは各repositoryに置き、共通のworkflowへ集約しません。

== 帰結

* 3つのrepositoryで同じtask名、同じRelease Notesの見出し、同じmanifestの必須項目、同じ作業規約を
  使えるため、手順を一つ覚えれば足ります。
* Release Notesの説明文がcodeからfileへ移るため、Release用Pull Requestの差分だけで公開内容を
  確認できます。代わりに、版を上げるときは``release/notes.md``の本文を書き直す必要があり、
  ``release-contract``がこの形を検査します。
* 必須checkが一つになるため、検査の追加や分割でGitHubのrulesetを変更する必要がなくなります。
  集約jobは個々の検査結果を``always()``で確認するため、検査のskipを成功と取り違えません。
* 共通schemaの``assets``を空にするAdocWeaveの扱いは、将来3製品で共通の検査toolを作る場合に、
  製品固有の拡張項目で公開assetを宣言する形を受理する必要があることを意味します。
* 書き込み権限を持つworkflowを共通化しないため、workflowの修正は各repositoryで個別に行います。
  これは権限境界をrepository単位に閉じるための意図的な選択です。
