= ADR 0046: ローカルファイル操作をプロジェクト処理へ統合
:status: accepted

== 状態

採用

== 背景

``adocweave-project``は、一回の要求に使う読込権限、設定、処理上限、取得結果および使用量を所有します。
一方、ローカルファイルを安全に開く低水準処理は``adocweave-host``にあり、専用のセッション、変更候補、対応関係、
処理単位およびキャッシュを介して利用していました。これらは長期状態や複数要求の調停を想定していましたが、現在のプロジェクト処理は
一回の``ProjectRequest``内で取得結果と使用量を固定します。Language Serverの長期状態も接続単位の``Session``が
所有するため、ファイル操作だけの独立した状態機械は必要ありません。

ファイルの読込権限を別クレートに置くと、``ProjectAuthority``が所有するルートディレクトリと処理上限を低水準の型へ変換し、
取得結果を再びプロジェクトの結果へ戻す必要があります。この変換は権限と使用量の正本を分散させます。

== 決定

開いたルートディレクトリのファイルハンドル、パスの検査、ファイルの読込と存在確認、明示されたディレクトリの走査および
安全な置換に必要な最小の処理を、``adocweave-project``の非公開モジュールへ移します。``ProjectAuthority``が開いた
同じ権限を``ProjectObserver``と``ProjectWriteCapability``も保持し、監視や書込のたびにルートディレクトリを
パスから開き直しません。

ファイル件数、読込量および関連リソースの結果は、既存の``ProjectResourceLimits``、``ProjectUsage``および
``ProjectResourceResult``を正本とします。ファイル操作専用のセッションID、版、変更候補、対応関係の世代、
反映、取消し、処理の調停役およびローカル参照先のキャッシュは設けません。取得した本文、ファイル不在および失敗は
``ProjectRequest``の処理中に直接固定します。

プロジェクトが公開するソース識別子にはコアの``SourceId``を使います。ファイルシステム固有の識別子やエラー型は
公開APIへ出しません。``ProjectObservationSession``は責務を直接表す``ProjectObserver``へ変更し、
``ProjectObservationAccess::observer``から作ります。旧名の別名や再公開は提供しません。

Linuxでは、開いたルートディレクトリのファイルハンドルを起点にパスを解決するADR 0014の安全性を維持します。
ルートディレクトリや祖先ディレクトリの差替え、シンボリックリンク、通常ファイル以外の対象および検査後の差替えを、
同じファイルハンドルに対する操作で拒否または安全側に処理します。書込時も対象の親ディレクトリを同じ権限から開き、
内容の再確認、一時ファイルの作成および名前変更を行います。内容の再確認と名前変更は別操作であるため、このAPIを使わない
書込元が同時に変更した場合まで、確認した内容に対してだけ置換することは保証しません。

macOS、Windowsおよびその他のOSでは、操作中にパスが変更されない静的な状態を前提として、ルートディレクトリの制限、
シンボリックリンクの検査、読込上限および置換前の内容確認を行います。Linuxと同じ、敵対的な同時変更への耐性は保証しません。
この違いを隠す汎用ファイルシステム層や独自の実行基盤は追加しません。

``adocweave-host``クレートは削除します。CLIとLanguage Serverは``adocweave-project``だけを通してローカルファイルを
扱い、個別のパス検査や使用量管理を実装しません。

== 検討した代替案

**``adocweave-host``を低水準処理だけのクレートとして残す。** ファイル操作を再利用できますが、現在の利用者は
``adocweave-project``だけです。独立クレートの公開APIと型変換が残り、権限と上限の正本が分かれるため採用しません。

**既存の状態機械を``adocweave-project``へ移す。** 従来のAPIを保てますが、一回の要求で完結する現在の処理に
セッション、変更候補、対応関係および処理単位の状態遷移を重ねることになります。長期状態を新たに所有するため採用しません。

**OSごとの処理を共通の公開トレイトで差し替える。** 外部実装を注入できますが、必要な権限と上限は
``ProjectAuthority``で決まっています。現在は別実装の利用要件がなく、保証の異なる処理を同じ型に見せるため
採用しません。

== 帰結

一回のプロジェクト処理における権限、取得結果、上限および使用量の正本が``adocweave-project``へまとまります。
ネイティブ版のクレート構成は``adocweave``、``adocweave-project``、``adocweave-cli``、``adocweave-lsp``、
``adocweave-wasm``および``adocweave-textlint``の6パッケージになります。

Rust APIの利用者は``adocweave-host``と、そのセッション、変更候補、対応関係および処理単位のAPIを利用できません。
``ProjectRequest``と``ProjectAuthority``を使い、一回の処理に必要な権限と上限を明示します。

Linuxの安全性試験では、保持したルートディレクトリ、祖先ディレクトリと末端のファイルの差替え、``openat2``を利用できない場合の
処理、procfsを利用できない場合の安全側の失敗、FIFO、名前に``(deleted)``を含むファイル、シンボリックリンクを追わない走査および
安全な置換を確認します。全OSで共有できるパスの正規化、ルートディレクトリの制限、上限および置換前の再確認は通常の試験で確認し、
その他のOS向けには既存の対象環境へクロスコンパイルできることも確認します。macOSとWindowsの実行環境を
使うCIでは、``adocweave-project``の試験を実行し、静的な状態を前提とするパス制限、シンボリックリンクの拒否、通常ファイルの
検査、読込上限および置換前の再確認を確認します。
