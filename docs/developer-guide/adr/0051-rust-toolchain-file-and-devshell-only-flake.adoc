= ADR 0051: 開発環境をrust-toolchain.tomlとdevShellだけのflakeで提供する
:status: 採用

== 状態

{status}

== 文脈

以前は、rootの``toolchains.json``がRustとNode.jsのバージョンを定めていました。Nixのflake、Nixのパッケージ定義
およびCIのworkflowがこのファイルを読み、使うRustやNode.jsのバージョンと一致するかを照合していました。flakeは、
入力と出力を``flake.nix``に宣言し、入力のリビジョンを``flake.lock``に固定するNixの形式です。このflakeは、
パッケージ（``packages``）、実行入口（``apps``）、検査（``checks``）と、5つのdevShell（``nix develop``で
起動する開発用のシェル）を公開していました。そのため、1つのバージョンの変更が、``toolchains.json``、
Nixの定義およびworkflowの複数のファイルへ波及していました。

一方で、rootには``rust-toolchain.toml``がありませんでした。このファイルは、リポジトリの中で使うRustの
バージョン、コンポーネントおよび構築先を定めるもので、rustupが読みます。ファイルがないため、rustupの利用者は、
各自が既定にしているRustで構築と検査をしていました。

開発環境を作り直すため、これらのNixの定義と``toolchains.json``は削除しました。

== 決定

rootの``rust-toolchain.toml``を、開発と検査に使うRustの唯一の定義とします。Nixから指定したバージョンの
Rustを導入できるようにするrust-overlayは、``fromRustupToolchainFile``関数でこのファイルからRustのバージョンを
読みます。このファイルはrustupも読むため、Nixの外で起動したエディタなど、rustupを通してRustを使うツールが
リポジトリの中で動く場合も、devShellと同じバージョンのRustを使います。

``channel``には``1.97.1``のような正確なバージョンを書きます。
``components``には、``clippy``と``rustfmt``に加え、エディタの補完などに使う``rust-src``と``rust-analyzer``も
含めます。``targets``には、Zed拡張を公式レジストリと同じ構築先向けに構築するための``wasm32-wasip2``を含めます。

``Cargo.toml``の``workspace.package.rust-version``は、常に``channel``と同じ値にし、同じコミットで更新します。
2つの値を照合する仕組みは作りません。開発と検査に使うRustが最小のバージョンそのものであるため、
``makers verify``の成功が、最小のバージョンで構築できることの確認になります。

``flake.nix``は``devShells.x86_64-linux.default``だけを公開し、定義は1つのファイルに収めます。この名前に
含まれる``x86_64-linux``はsystem、つまりNixがCPUとOSの組で表す実行環境で、IntelやAMDの64ビットCPUで動く
Linuxを指します。devShellの構築と``makers verify``の成功を確かめたのはこのsystemだけであるため、対象を
これに限ります。``packages``、``apps``、``checks``および``overlays``は公開しません。

devShellには、``makers verify``が実行するコマンドだけを入れます。検査を加える変更で新しいツールが必要に
なった場合は、同じ変更でdevShellへ加えます。``ps``のようにOSが標準で備えるコマンドはdevShellに入れず、
Nixの外の環境のものを使います。

Nixのパッケージ集であるnixpkgsは、安定リリースのchannel（現在は``nixos-26.05``）から取得します。Node.jsは
nixpkgsの``nodejs_24``を使い、``package.json``の``engines.node``とは照合しません。

``flake.lock``はコミットし、人が``nix flake update``で更新します。

開発に参加する人はNixを使うことを前提とし、Nixを使わずに開発環境を用意する手順は文書に書きません。

CIの実行環境は、このADRでは決めません。

本ADRはxref:0035-minimal-nix-flake-outputs.adoc[ADR 0035]とxref:0039-ci-shell-responsibility-boundary.adoc[ADR 0039]を
置き換えます。

== 検討した代替案

**共通のmanifestを戻し、各定義で照合する。** rustupとrust-overlayは``rust-toolchain.toml``を直接読むため、
別のmanifestを置くと、その値と``rust-toolchain.toml``を照合する仕組みが新たに必要になります。文脈で述べた
変更の波及が戻るため採用しません。

**``channel = "stable"``にする。** バージョンを上げる変更は不要になりますが、devShellのRustと、rustupを
通してRustを使うツールのRustは、それぞれがstableを解決した時点で決まるため一致しません。また、
``flake.lock``を更新すると、新しいRustが加えたlintにより、Rustのコードを変えていなくても検査が失敗することが
あるため採用しません。

**``flake.nix``へバージョンを直接書く、または``rust-version``を読む。** rustupは``flake.nix``も
``Cargo.toml``の``rust-version``も読みません。rustupを通してRustを使うツールが、devShellと同じRustを
使えなくなるため採用しません。

**nixpkgsの``rustc``を使う。** rust-overlayの入力は不要になりますが、Rustのバージョンがnixpkgsのリビジョンで
決まり、rustupを通してRustを使うツールが使うバージョンとそろえられないため採用しません。

**fenixを使う。** fenixは、Rustを導入する別のNixの定義集で、``rust-toolchain.toml``も読めます。ただし、
ファイルのほかにRustの配布物の一覧（manifest）のハッシュ値``sha256``を指定する必要があり、
バージョンを上げるたびにその値も更新することになるため採用しません。

**用途別に複数のdevShellを作る、または定義を``nix/``へ分割する。** 用途ごとに導入するツールを絞れますが、
devShellが1つの小さなflakeでは、読む場所が増えるだけで読みにくくなるため採用しません。

**ARMのLinuxとApple SiliconのMac（``aarch64-linux``と``aarch64-darwin``）も対象にする。** それらの
コンピュータでも``nix develop``を使えるようになり、加える定義も短く済みます。ただし、devShellの構築と
``makers verify``の成功を確かめたのは``x86_64-linux``だけで、確かめていない環境を対象として示すことに
なるため採用しません。

**``rust-version``を開発用のバージョンと別に管理する。** 利用者に古いRustでの構築を認められますが、
開発と検査が別のバージョンを使うと、最小のバージョンで構築できることを確かめる検査がなくなります。
そのため採用しません。

**Nixを任意にして、rustupによる手順も残す。** Nixを使わない人も文書の手順で開発環境を用意できますが、
2つの手順を保守し、両方を確かめる必要があるため採用しません。

== 帰結

Rustのバージョンを上げる変更は、``rust-toolchain.toml``の``channel``と``rust-version``の2行で済みます。
ただし、``flake.lock``で固定したrust-overlayが新しいバージョンを知らない場合は、``flake.lock``の更新も
必要です。その場合はdevShellの評価が失敗するため、更新が必要なことに気付けます。

開発に参加するには、flakeを有効にしたNixが必要です。Nixを使えない環境では、文書の手順で開発環境を
用意できません。``x86_64-linux``以外のsystem（ARMのLinuxやApple SiliconのMacなど）では、このflakeで
開発環境を用意できません。ほかのsystemを対象にするには、そのsystemでdevShellの構築と``makers verify``の
成功を確かめたうえで、flakeへ加えます。

devShellの外でrustupを通してRustを使うツールがリポジトリの中で動くと、rustupは``rust-toolchain.toml``が
指定するRustを、コンポーネントと構築先を含めて導入します。

Zed拡張も、公式レジストリが使うRustではなく、``rust-toolchain.toml``のRustで構築します。公式レジストリの
Rustで構築できることは、手元の検査では確かめません。

devShellはOSが標準で備えるコマンドを含みません。そのため、``nix develop -i``のようにホストの環境変数を
引き継がずに起動すると、``ps``を使うテストが失敗します。

このflakeは``packages``と``apps``を公開しません。Nixでの配布は、このADRでは決めません。
