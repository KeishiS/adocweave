= ADR 0041: CLIとLanguage Serverのプロジェクト処理責務
:status: partially superseded by ADR 0044

== 文脈

CLIは一つのコマンドを実行して終了します。Language Serverは、開いている文書、未保存の内容、設定、
ファイルの変更および解析結果を継続して扱います。この二つが、文書内容、includeの依存関係および
解析結果を保持する変更可能な``Workspace``を共有すると、CLIにも継続的な状態管理が必要になります。
Language Serverでは、開いている文書と``Workspace``の内容を二重に対応付ける処理も必要です。

includeの依存関係とは、文書と、その文書が読み込むinclude先の対応関係です。ADR 0012では、
ファイル操作を行う処理と、固定した入力だけを使う解析を分けました。一方、どの層が状態を継続して
保持するかは、``adocweave-workspace``の状態遷移の実装を読まなければ分かりません。

本ADRでは、現行APIとの互換性を要件とせず、CLIとLanguage Serverに必要な責務を分けます。
長期状態を持つ汎用的なサービス、別プロセスおよび独自の通信規約は追加しません。

== 決定

=== 四つの責務

プロジェクトの処理を、次の四つへ分けます。

* *CLI*: 一つのコマンドに必要な解析対象のファイル、設定の上書き、ファイル読込みの許可範囲および
  処理上限を渡し、結果を出力します。文書内容、includeの依存関係および解析結果をコマンドの終了後まで
  保持しません。
* *Language Serverのセッション*: 開いている文書、未保存の内容、現在の設定、プロジェクトルート、
  ファイル読込みの許可範囲および利用者へ提示する最新結果を保持し、ファイルの変更と実行中の処理を
  管理します。変更されていないファイルの内容とincludeの依存関係を再利用する場合も、このセッションが
  所有します。
* *要求単位のプロジェクト処理*: 一度の解析要求に必要なファイルを安全に読み、固定した入力でコア解析を
  実行します。呼出元が必要な結果を返し、次の要求でも再利用する状態は持ちません。
* *コア解析*: 呼出元から渡された固定入力だけを解析します。ファイル操作、非同期処理を動かす仕組みおよび
  LSPの型には依存しません。

Language Serverのセッションは、LSPの初期化から終了までの一つの接続に対応します。一つのセッションが、
複数のプロジェクトルートと、それぞれの許可範囲を所有できます。プロジェクトルートごとの状態は、
そのルートがセッションへ追加されてから削除されるまで保持します。

固定した入力とは、一度の解析で使う設定と文書内容の組であり、その解析中には変更しません。
要求単位のプロジェクト処理は、CLIとLanguage Serverが同じプロセス内で直接呼び出す関数として提供します。
長期状態を所有する``WorkspaceService``、常駐プロセスまたは内部通信を設けません。

=== Language Serverが保持する状態

Language Serverは、解析に使う文書、ファイル上の内容、設定、プロジェクトルートおよび読込みの許可範囲の
組を識別する値を発行します。本ADRでは、この値を入力版と呼びます。いずれかの内容が変わると、入力版も
変わります。入力版の具体的な型や、入力版を内部でいくつの値に分けて管理するかは定めません。

Language Serverは、要求単位のプロジェクト処理を始める前に入力版をその解析処理の状態へ記録します。
プロジェクト処理の要求と結果には入力版を含めません。Language Serverは、記録した入力版が現在値と一致し、
処理が取り消されていない場合だけ、次の情報を一括してセッションへ反映します。

* 新たに読み込んだファイルの内容
* 実際に使ったincludeの依存関係
* 監視対象とする、存在しないinclude先または読み込めなかったinclude先の情報
* 解析結果

入力版が古い場合は、これらをすべて破棄します。古い処理から得たファイル内容や依存関係の一部だけを、
新しいセッションの状態へ取り込むこともありません。一括反映によって入力の集合またはincludeの依存関係が
変わった場合は、新しい入力版を発行します。同じ入力版から始まった後続の結果は古いものとして扱います。

文書のURIは、Language Serverとエディタの間で文書を示す識別子です。Language Serverは、URIを検証し、
処理内で文書を一意に示す論理IDへ一度だけ対応付けます。未保存の内容は、同じ論理IDを持つファイル上の
内容より優先します。要求単位のプロジェクト処理とコア解析は同じ論理IDを使い、LSPのURIを扱いません。

一度の要求で読み込んだ文書には、要求が終わるまで同じ内容を使用します。同じ実体を指す複数の論理IDは
区別しますが、安全性を確認した同じファイルの取得結果は一度の要求内で共有します。ただし、すべてのファイルが
同一時点に持っていた内容を読み込むことは保証しません。ファイルは順に読み込まれるため、別の処理が
途中で書き換えた場合は、異なる時点の内容が同じ要求に含まれることがあります。結果を反映する時点の
入力版の確認により、既知の変更後に古い結果を利用者へ提示することは防ぎます。

=== 要求単位のプロジェクト処理

要求単位のプロジェクト処理は、少なくとも次の情報を明示的に受け取ります。

* プロジェクトルートと解析対象
* 設定ファイルの指定と要求単位の上書き
* 論理IDに対応付けた未保存の内容
* 検証済みのプロジェクトルートへ結び付いたファイル読込みの許可範囲
* includeの深さ、ファイル数、読込み量および走査件数などの安全上限
* 取消しの確認方法

この処理は、安全なファイル読込みとコア解析を一度の要求の中で順に実行します。固定した解析入力、解析結果、
読み込んだファイルとその取得元、監視が必要なinclude先および処理上限の使用状況を結果として返します。
ファイル読込みを行う部品やコア解析の具体的な型、crateおよびモジュール配置は、実装時に決めます。

プロジェクト設定の探索と読込みも、要求単位のプロジェクト処理が同じ許可範囲で行います。Language Serverは、
プロジェクトルートの追加または設定ファイルの変更を検知したとき、この処理を新しい入力版で開始します。
設定に記載されたパスは、利用者がコマンドまたはLSPで許可した範囲を広げません。

=== 解析中に必要になるファイル

文書属性によって参照先が変わるincludeなど、解析して初めて読むファイルが決まる場合があります。
コア解析はファイルを直接読み込まず、参照元の論理IDと、属性を適用して得た参照先をファイル要求として返します。
OS上のパスへの変換と、どのプロジェクトルートから読めるかの確認は、要求単位のプロジェクト処理が行います。
文書間の参照や画像など、ファイルの存在や種類だけを確認するlocal target検査も、同じ要求単位の処理が行います。
includeの本文読込みとlocal target検査には、同じ許可範囲と安全上限を適用します。

要求単位のプロジェクト処理は、各ファイル要求の結果を次のいずれかとして一度の要求内に記録します。

* 読込み済み
* ファイルが存在しない
* 文字コードなどの問題により読込み不可
* 許可範囲、安全性の確認または処理上限により拒否

ファイル要求に対応する内容を読み込めた場合は、その内容を加えた固定入力でコア解析をやり直します。
存在しない場合と読み込めない場合も、その結果をコア解析へ渡し、同じファイルを繰り返し要求しないようにします。
新たに得られるファイル内容や読込み結果がなければ反復を終了します。includeの深さ、ファイル数、読込み量および
反復回数には、一度の要求で共有する安全上限を適用します。

存在しないファイルと、文字コードなどの修復可能な問題があるファイルは、解析結果に対応する診断を含め、
Language Serverの変更監視へ登録します。そのファイルが作成された場合、または内容が修正されて読み込めるように
なった場合は、必要としていた文書だけを解析し直します。許可範囲外の参照先、不正なURIおよび安全性を
確認できない参照先は監視へ登録しません。

コア解析へ、解析中にファイルを取得するための関数は渡しません。これにより、ファイル読込みの許可範囲と
処理上限を要求単位のプロジェクト処理へ集約し、コア解析を同じ入力から同じ結果を得られる処理として維持します。

=== 変更の反映とプロジェクトの走査

Language Serverは、文書、設定またはファイルの変更を検知すると、セッションに保持しているファイル内容、
includeの依存関係および解析結果のうち、影響するものを破棄して新しい要求を開始します。設定変更では、
変更された項目に応じて解析結果、ファイルの探索結果または読込みの許可範囲を破棄します。設定変更のたびに
プロジェクト全体を走査することは要件としません。

プロジェクト内の対象ファイルを探すための走査は、初期化、プロジェクトルートや走査設定の変更、および
変更監視の通知を信頼できなくなった場合の再構築に使います。文書を編集するたびに、変更されていない
ファイルをすべて読み直しません。走査から除外した場所でも、明示的に開いた文書と許可されたinclude先は
読み込めるというADR 0019の規則を維持します。

変更通知の欠落、監視情報の上限超過または監視処理のエラーにより、現在のプロジェクト状態を把握できない場合は、
影響するプロジェクトルートの状態を安全に再構築します。変更通知をまとめる待機時間、同時に実行する処理数
および再利用する内容の保存方法は、本ADRでは定めません。

=== ファイル読込みの許可範囲と処理上限

ADR 0014で決めた安全なファイル読込みを維持します。先に安全性を確認して開いたプロジェクトルートの
ディレクトリを起点として対象を開き、検査したファイルと実際に読んだファイルが同一であることを確認します。
ファイル読込みの許可範囲は、この安全性を確認して開いたディレクトリのファイルハンドルと結び付けます。

CLIは、この許可範囲を一つのコマンドが終わるまで保持します。Language Serverは、対応するプロジェクトルートが
セッションに含まれる間だけ保持します。長期間保持するのは検証済みのプロジェクトルートと許可範囲であり、
本文の取得結果と要求の処理上限は要求単位とします。現行の長期状態を持つ``LocalFilesystemSession``による
本文の再利用、処理上限および``Draft``の管理は維持しません。include先には、参照元の文書に対応する
許可範囲を適用します。

対象ファイルを探す走査が安全上限に達した場合は、ADR 0025に従い、そこまでに安全に見つけた解析対象と警告を
残します。要求単位のファイル読込みが上限に達し、include先を取得できない場合は、その文書を必要なinclude先を
すべて反映した完全な解析結果として扱いません。以前に提示した安全な結果は維持し、上限に達したことを通知します。

許可範囲からの逸脱、シンボリックリンクの検査失敗または読込み内容の同一性を確認できない場合は、
安全でない入力、依存関係および解析結果をセッションへ反映しません。単なるファイルの不存在や修復可能な
読込みエラーとは区別します。

=== 現行設計の置換

ADR 0012で決めた、変更可能な``Workspace``へ、ファイル上の内容と未保存の内容を重ねる仕組み、includeの依存関係、
世代および解析結果を集約する設計は置き換えます。CLIとLanguage Serverで共有するのは、要求単位の
プロジェクト処理とコア解析です。長期状態を共有する役割としての``Workspace``、``Draft``および
``Transaction``は廃止します。
型名と内部配置は実装時に決め、移行用の互換APIは設けません。

ADR 0012のうち、解析中にファイル操作を行わないこと、固定した入力を使うこと、取消しを確認できること、
古い結果を反映しないことは維持します。ADR 0014の安全なファイル読込み、ADR 0019の走査除外とinclude先の
変更監視、およびADR 0025の走査上限に達した場合の部分結果という保証も維持します。各処理の所有者だけを
本ADRの決定に合わせて変更します。

ファイル内容を保持する仮想ファイルシステム（VFS）と、呼出元から渡された入力だけを解析するAPIの分離を
参考にします。
link:https://docs.astral.sh/ruff/editors/[Ruffのエディタ統合]にある、既存の検査・整形処理をLanguage Serverから
利用する構成と、link:https://docs.astral.sh/ruff/editors/settings/[Language Serverによる設定の管理]を
参考にします。
link:https://docs.deno.com/runtime/reference/lsp_integration/#structure[DenoのLanguage Server構造]にある、
Language Server固有の状態を``LanguageServer``が所有する分け方も参考にします。

これらのOSSの内部構造は再現しません。rust-analyzerが使用する、変更の影響を受ける部分だけを再計算する
データベース、Denoの内部モジュール構成およびRuffのPython固有機能は導入しません。ファイル読込みを行わない
解析APIと、Language Server固有の状態をLanguage Serverが所有する責務分担だけを採用します。

== 検討した代替案

**共通の変更可能な``Workspace``。** CLIとLanguage Serverが同じ状態遷移を使えます。一方、CLIには不要な
長期状態が加わり、Language Serverでは開いている文書と共通``Workspace``の状態を二重に対応付ける必要があります。

**長期状態を持つ``WorkspaceService``。** 利用側は統一したAPIを呼べますが、プロセスの寿命、非同期処理、
再利用のため保存する内容、変更時にそれを破棄する処理および取消しを、汎用サービスへ集約する必要があります。
CLIにも長期状態の保持期間、取消しおよび再利用を管理させる構成になるため採用しません。

**編集のたびにプロジェクト全体を読み直す構成。** 状態の管理は単純になりますが、大きなプロジェクトで
不要なファイル操作と解析が増えます。変更の影響を受ける文書だけを解析し直す構成を採用します。

**増分計算用データベース。** 依存関係と再計算を統一できますが、現在必要な文書単位の再解析に対して導入と
保守の負担が大きいため採用しません。必要性が明確になった時点で別のADRとして判断します。

**別プロセスと独自通信規約。** 複数の利用側で状態を共有できますが、起動、互換性、障害時の対処および
通信規約の保守が必要です。CLIとLanguage Serverを同じ``adocweave``実行ファイルへ統合するADR 0040にも
不要な構成であるため採用しません。

== 帰結

CLIは一度の要求に必要な情報だけを渡し、Language Serverは継続して必要な状態だけを所有します。
コア解析はファイル操作やLSPの型へ依存せず、CLI、Language ServerおよびRustライブラリから再利用できます。
未保存の内容の優先とincludeの変更検知は、一つのLanguage Serverセッション内で一貫して扱えます。

現行の共通``Workspace``とLanguage Serverによる二重の状態管理は不要になります。変更されていないファイルを
再利用する場合はLanguage Serverだけがその情報を所有します。CLIと共有する長期状態、専用サービス、別プロセス
および独自通信規約は不要です。

一度の要求では各ファイルの内容を固定しますが、すべてのファイルが同一時点の内容であることは保証しません。
既知の変更後に古い結果を利用者へ提示しない保証は、Language Serverが入力版を確認することで提供します。
