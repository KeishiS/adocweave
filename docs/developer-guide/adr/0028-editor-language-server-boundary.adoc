= ADR 0028: エディタとLanguage Serverの導入方法の分担
:status: 一部有効。実行ファイルはADR 0040、配布方法はADR 0043により改訂

== 状態

{status}

== 文脈

VS Code拡張とZed拡張はLanguage Serverのclientですが、これまで各拡張が配布manifestの取得、platform判定、
archiveとhashの検証、展開、cache、排他制御および障害からの復旧も実装していました。同じ導入処理を異なる
editor API上で保守する必要があり、Language Serverの配布仕様を変えるたびに両拡張の変更と検証が必要でした。

ADR 0027は、六製品のrelease trainを分ける一方で、``lspApiVersion``と``managedLspVersion``によって拡張が
特定のLanguage Serverを管理することを決めました。この仕組みは版番号の完全一致を避けますが、拡張が
Language Serverを配布・更新する責務と、独自の互換性判定を残します。LSPには初期化時にclientとserverが
対応機能を交換する標準のcapabilityがあります。

== 決定

=== 製品と導入方法の分担

Language Server、VS Code拡張およびZed拡張は、引き続き異なる製品バージョン、tagおよびGitHub Releaseを持ちます。
拡張へLanguage Serverを同梱しません。

拡張はエディタで有効な設定の絶対path、editor processから見える``PATH``、自動取得の順で
``adocweave-lsp``を探します。利用者が導入した実行ファイルを常に優先し、自動取得は最後の手段とします。
自動取得した実行ファイルの導入先は拡張が所有し、利用者が導入したものへ影響しません。

自動取得は、公開済みGitHub Releaseのうちtagが``adocweave-lsp/v``で始まるものから最新版を選びます。
拡張はLanguage Serverの版を固定せず、``managedLspVersion``のような対応版の宣言を持ちません。取得済みの版は
残し、同じ版を取得し直しません。対応するplatformの成果物がない場合は自動取得へ進まず、対応するOSと
architectureを示して失敗します。

=== 取得したarchiveの検証

検証できる場合は検証します。VS Code拡張はNode.jsで動くため、同じReleaseの``sha256.sum``に記載された値と
照合してから展開します。一致しない場合は展開せず、理由を示して起動を中止します。Zed拡張は照合しません。
Zedの拡張APIには、取得したfileをbyte列として読む手段もhashを計算する手段もないためです。

attestationの検証はどちらの拡張でも行いません。sigstoreの検証処理を拡張へ組み込む必要があり、
checksumの照合に比べて費用が大きいためです。

未信頼のprojectまたはworktreeの設定から任意の実行ファイルを起動しません。VS Codeは未信頼ワークスペースで
拡張を無効にし、ZedはWorktree Trustに従います。

Language Serverの導入、検証、更新、rollbackおよび削除を利用者が自分で行う経路は維持します。共通の導入手順、
Nixおよびpackage registryは引き続き利用でき、そこではchecksumとattestationを検証できます。

Language Server processの起動、標準入出力による通信、初期化、停止、再起動および異常終了の処理は、
VS CodeとZedが提供する標準LSP client APIへ委ねます。拡張独自のprocess監視と終了手順を設けません。

=== 互換性の判定範囲

拡張とLanguage Serverの製品バージョン、``lspApiVersion``または固定した対応版の一覧を互換条件にしません。
LSPの``initialize``で交換する標準capabilityを、利用できる機能の判定基準とします。editorのLSP clientはLanguage Serverが宣言した
capabilityに対応する機能だけを有効にします。拡張は起動前の独自検査を追加せず、標準の初期化に失敗した場合だけ
起動失敗として理由を利用者へ示します。

AdocWeave固有のrequest、responseまたは通知を将来追加する場合は、その機能の有無を明示的に交渉します。
製品全体を一つの整数へ対応付ける互換性検査には戻しません。

== 検討した代替案

**自動取得を持たず、共通の導入手順だけを案内する。** 拡張と配布工程の責務は小さくなりますが、拡張を導入した
利用者が別の手順を踏むまで解析を使えません。実際にZedでこの状態が報告されました。Zedの言語拡張は自動取得と
``PATH``探索のどちらも一般的で、``PATH``のみとしているものはLanguage Serverが言語のtoolchainへ同梱される
場合が中心です。``adocweave-lsp``は単体配布のbinaryであり、この条件に当てはまりません。

**Language Serverを拡張へ同梱して同時に公開する。** 組み合わせは固定できますが、Language Serverだけの修正でも
両拡張の再公開が必要になり、ADR 0027で分けたrelease trainを再び結合します。

**拡張が対応するLanguage Serverの版を宣言する。** 取得先は決まりますが、Language Serverを更新するたびに拡張の
再公開が必要になり、release trainを分けた意味が薄れます。公開済みreleaseから最新版を選びます。

**製品バージョンまたは``lspApiVersion``を事前に検査する。** 実際に利用できるLSP機能を間接的な番号から推測する
検査処理が増えます。標準の初期化処理で交換するcapabilityを直接確認します。

== 帰結

エディタ拡張を導入すれば、追加の手順なしで文書解析を利用できます。Language Serverをすでに導入している
利用者は、設定または``PATH``によってこれまでどおりその実行ファイルが使われます。

自動取得の完全性は、拡張によって程度が異なります。VS Code拡張はchecksumを照合するため、改変または破損した
archiveを展開しません。Zed拡張は照合できないため、完全性はTLSだけに依存します。導入の手間を減らすことを
優先した判断です。どちらもattestationは検証しません。より強い保証が必要な利用者は、共通の導入手順、Nixまたは
package registryから導入し、その実行ファイルを設定または``PATH``で指定します。

Language Serverの更新時期を利用者が選ぶ場合は、自動取得ではなく明示的な導入を使います。自動取得は、拡張が
公開済みreleaseの最新版を選びます。

managed downloadを提供していた旧拡張のcacheは更新だけでは削除されません。旧版の削除機能または共通導入文書の
手動手順で一度だけ削除します。

ADR 0013とADR 0023にある拡張とLanguage Serverを同時に配布して完全一致を要求する決定、およびADR 0027にある
``lspApiVersion``、``managedLspVersion``と自動取得の決定を本ADRで置き換えます。ADR 0027の製品別release trainと、
ADR 0023の公開先と権限制限は維持します。候補SHAと過去candidateの再利用は
xref:0032-same-run-release-publication.adoc[ADR 0032]で置き換えます。
