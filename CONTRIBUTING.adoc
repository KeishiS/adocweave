= コントリビューションガイド

AdocWeaveへの変更は短命なブランチで作業し、pull requestを通してmainへ統合します。

== 開発環境

開発環境はNixで提供しています。リポジトリのrootで次を実行してください。

[source,console]
----
nix develop
cargo make verify
----

日本語文書だけを読み取り専用で校正する場合は、次を実行します。このtaskは必要なNode.js依存と専用の
WebAssemblyを構築しますが、文書を自動修正しません。

[source,console]
----
cargo make docs-prose-lint
----

``cargo make verify``はPull Request用の標準検査であり、``cargo make``の既定taskです。ソース、依存関係、
Nixパッケージ、browserおよびeditor adapter、HTML5標準適合性、文書をまとめて検査し、fuzz targetが既知の入力で
落ちないことを確認します。

次のtask名は、並行して開発するMarginalis、Renkanと共通の外向きの名前です。repositoryが変わっても
同じ名前で同じ意味の検査を実行できます。

[cols="1,3",options="header"]
|===
|task |意味

|``fmt`` / ``fmt-check``
|ソースの整形と、整形済みであることの検査

|``verify``
|Pull Request用の標準検査（既定task）

|``security-audit``
|依存関係の出所、license、advisoryおよび例外の監査（``dependency-governance``と同じ）

|``acceptance``
|``verify``に加え、CIが行う自動受入検証のうち現在のhostで実行できるもの
 （global成果物の実Chromium検査、native smoke、installation E2E）

|``release-check``
|公開前の完全な検査
|===

== 作業の進め方

. ``main``を最新にし、変更の目的に合う短命なブランチを作成します。GitHub上のこのリポジトリを指す
  remote名は``upstream``とします。
+
[source,console]
----
git switch main
git pull --ff-only upstream main
git switch -c fix/browser-archive-import-check
----
+
ブランチ名の付け方は<<branch-names>>を参照してください。

. 一つのブランチでは一つの目的に集中し、実装と対応するテストとドキュメントを更新します。
. 変更をコミットする前に検証を実行します。
+
[source,console]
----
cargo make verify
----

. ブランチをpushしてpull requestを作成し、squash方式のauto-mergeを設定します。必須check``verify``が
  成功すると``main``へ統合されます。``main``へ直接pushしません。
+
[source,console]
----
git push -u upstream fix/browser-archive-import-check
gh pr create
gh pr merge --auto --squash
----

. ``main``が先へ進んで競合した場合は、rebaseではなく``upstream/main``をブランチへmergeして解消します。
  squash mergeで履歴は1 commitにまとまるため、ブランチ上のmerge commitは``main``へ残りません。
+
[source,console]
----
git fetch upstream main
git merge upstream/main
----

. pull request完了後は作業ブランチを削除します。

競合の解消が難しい場合や変更の目的が増えた場合は、pull requestを分割します。
remote名、ブランチ名、mergeの方式および必須checkの構成は、Marginalis、Renkanと共通です
（xref:docs/developer-guide/adr/0021-common-development-contract.adoc[ADR 0021]）。

[#branch-names]
== ブランチ名

ブランチ名は``種別/目的``の形にします。目的の部分は、ブランチの一覧を見たときに何をしているか
分かる長さにします。

[cols="1,3",options="header"]
|===
|種別 |用途

|`feat/<topic>`
|利用者に見える機能の追加

|`fix/<topic>`
|不具合の修正

|`refactor/<topic>`
|外部の意味を変えない内部構造の整理

|`perf/<topic>`
|外部の意味を変えない性能の改善

|`ci/<topic>`
|CI、build、release、開発環境の変更

|`docs/<topic>`
|文書だけの変更

|`chore/<topic>`
|上のいずれにも当たらない保守作業
|===

人以外が作業する場合は、作業主体を先頭に付けて``agent/<種別>/<目的>``とします。どのブランチを人が
確認すべきかが一覧から分かるようにするためです。この形は3製品で共通です。

== 変更時の確認

* 不具合修正には、可能な限り再発を防ぐテストを追加します。
* 依存関係を更新する場合は、対象のlockfileだけを更新し、``cargo make dependency-governance``を実行します。
* Nix flakeまたはパッケージを変更する場合は、``cargo make nix-package-check``を実行します。
* ``.adoc``文書は既存の用語と書式に合わせます。
* 比較用の期待出力は、実際の出力との差分を確認し、意図した変更である場合だけ更新します。
* AsciiDoc構文を変更する場合は、`docs/user-guide/syntax-support.adoc`、`docs/user-guide/compatibility.adoc`、
  `docs/developer-guide/grammar.adoc`、対応するテスト用入力およびテストを更新します。

**新しいAsciiDoc構文を追加する**場合は、同じ変更で次を定義します。言語へ要素を足す判断であるため、
後から決め直すと解析結果とエディタの挙動が揺れます。

. 字句とEBNFまたは同等の認識規則を定義します。
. 既存のblock構文とinline構文に対する認識優先順位を定義します。
. 構文情報から意味情報への対応と、保持する元範囲を定義します。
. 不完全入力の同期点、回復結果および安定した診断codeを定義します。
. 厳格modeと寛容modeでの扱いを定義します。
. 曖昧入力、境界値および回復をテスト用入力と期待結果で固定します。

既存構文の**不具合修正や挙動の調整**では、この6項目を求めません。再発を防ぐテスト用入力と期待結果を
追加すれば十分です。認識規則そのものを変える場合だけ、上の項目のうち影響する範囲を更新します。

[#dependencies]
== 依存関係

依存境界、許可するlicenseと取得元、および一時的な例外は``security/``以下の機械可読な設定を
基準とします。文書へパッケージ一覧やバージョンを転記しません。

依存関係を更新するときは次を確認します。

. 対象のmanifestとlockfileだけを更新し、無関係な依存境界の変更を分離します。
. RustSec Advisory Databaseの固定revisionを更新し、新しいadvisoryを確認します。
. ``cargo make dependency-governance``を実行します。
. license、取得元、生成されるnotice、SBOMおよびbrowser sizeの差分を確認します。
. 通常の品質検査を通してからpull requestを統合します。

同じcrateの複数バージョンが依存関係へ入ることは禁止しません。上流のバージョン制約で決まる値であり、
一覧を保守しても実害を防げないためです。重複が問題になるのは成果物の大きさとbuild時間であり、
これらはbrowser archiveとraw WebAssemblyの上限、VSIXのsize上限および``wasm-size``が検査します。

VS Code拡張の依存は、配布物へ同梱するものと、CIおよびVSIX生成で実行するものを別の方針で扱います。
どちらも取得元をnpm registryに限り、sha512のintegrityを求めます。同梱する依存には利用者に対する
license上の義務があるため、許可するlicenseを限定します。ビルド用の依存は利用者の環境で動かないため
同梱する依存より広い範囲を許し、許可するlicenseを
link:security/vscode-build-licenses.json[`security/vscode-build-licenses.json`]へ記録します。
一覧に無いlicenseが現れた場合だけ検査を失敗させます。使われなくなったlicenseを一覧から消す必要は
ありません。
脆弱性は、同梱する依存だけを対象とする監査と、ビルド用を含む全体の監査の両方を実行します。

Advisoryを一時的に除外する場合は、RustSec advisory ID、担当者、影響しないと判断した理由、将来の期限および
追跡Issueを記録します。包括的な除外や無期限の例外は追加しません。期限切れの例外は検査を失敗させます。

Dependabotのpull requestでも通常のreviewと必須検査を省略しません。Cargo更新ではlockfile、license、取得元、
advisoryおよびRust stableへの影響を、GitHub Actions更新では完全なcommit SHAへの固定とRelease Notesを
確認します。

[#dependabot-updates]
=== Dependabotの手動merge

DependabotのPull Requestは更新範囲にかかわらず自動mergeせず、人が変更内容と必須検査を確認して統合します。
リポジトリにはDependabotのauto-mergeを登録するworkflowとwrite権限を置きません。

reviewでは、manifestとlockfileの差分、直接・間接依存関係、SemVerの更新範囲、security advisory、
license、取得元および生成されるnoticeとSBOMを確認します。GitHub Actions更新では完全なcommit SHAへの
固定と上流Release Notesも確認します。必須検査、競合確認および最新の``main``への追従を省略しません。

自動mergeを再検討する場合は、同じ管理者が作成した通常のPull Requestを統合できるreview体制、
Dependabot alertを完全に取得できるActions権限、strictなrulesetおよびalert照会後の時間差を解消する設計を
新しいIssueで扱います。設定やworkflowを直接追加して開始しません。

Nix入力はDependabotの対象外であり、``flake.lock``を手動で更新します。Frontendへruntime dependencyを追加する
場合は、lockfileに基づくSBOM生成を先に実装します。

== 文書を増やさない規則

文書の重複と陳腐化を避けるため、次の規則に従います。

* 新しい文書を追加する前に、既存の文書へ統合できないか確認します。
* 利用者向けの手順は代表的な経路だけを書きます。成果物ごとの網羅した手順を並べず、詳細はCLIのhelpと
  Release Notesへ委ねます。
* バージョン固有の変更内容と移行手順は、原則としてGitHub Release Notesへ記載します。その本文は
  ``release/notes.md``に書き、版を上げるときに書き直します。Release本文がMarkdownであるため、このfileだけは
  ``.adoc``ではなく``.md``です。VS Code拡張の``editors/vscode/README.md``も、拡張registryとeditorの拡張画面が
  Markdownだけを表示するため``.md``です。
* CLI option、診断code、パッケージバージョン、対応target、公開APIおよびschemaなど、codeや機械可読な
  manifestから取得できる情報を文書へ重複して記載しません。
* 現行仕様、設計理由および作業計画を同じ文書に混在させません。現行仕様は``docs/``、設計理由はADR、
  作業計画はGitHub Issuesを正本とします。
* 完了した作業の経緯はGit履歴とGitHub Issuesで確認し、リポジトリ内にIssue台帳を複製しません。
* 利用者から見える変更では、関連文書を同じpull requestで更新します。
* 文書内のcommand例は、可能な限りCIまたは自動testで実行できる形にします。

== Pull request

pull requestを作成するときは、link:.github/pull_request_template.md[Pull Request template]を使用します。
変更の目的、主な変更点、実行した検証を簡潔に記載し、未実施の検証がある場合は理由を記載してください。

CIの必須checkは``verify``の一つだけです。``verify``は、dependency governance、source quality、fuzz、
Nixパッケージに加え、変更に応じて選択したcandidate build、smoke testおよび
installation E2Eの結果を``always()``で集約します。個々の検査がskipされた場合も、必要な検査が成功したか
どうかをこのjobが判定するため、検査のskipを成功と取り違えません。失敗した場合は、該当する``cargo make``
taskをNix開発環境で再実行し、設定の基準である``.github/workflows``と``Makefile.toml``を確認してください。

source qualityは、書式や生成ファイルなどの短い検査、Rustワークスペースの検査、WASM・browser・editor adapterの
検査に分けて並列実行します。
成果物を構築するPull Requestでは、書式、生成ファイル、workflow、``release-contract``および
変更pathの分類を``cargo make ci-preflight``で先に確認します。global成果物へ影響する場合は、
実Chromiumによるarchiveの受入検査もPull Requestで実行します。

``cargo make verify``はsource gate、dependency governance、fuzzおよびNixパッケージ検査を含みますが、
実Chromiumによる受入検査は含みません。browser、ZedまたはVS Code向けの成果物へ影響する変更では、
次を実行してCIの``build-global``と同じ範囲を手元で確認してください。

[source,console]
----
cargo make verify-with-global-candidate
----

このtaskは``cargo make verify``に加えて、配布するbrowser、ZedおよびVS Codeのarchiveを構築し、
cross-origin isolationを使わない静的配信環境およびbundler経由の2経路で実Chromiumから実行します。

手元とCIでは、``flake.lock``で固定した開発環境のChromiumを使用します。別のbrowserを確認する場合は
``ADOCWEAVE_BROWSER``で実行ファイルを指定できます。

[#tag]
== Tag

安定版には``vX.Y.Z``形式のtagを使用します。人がtagを直接作成またはpushしてはいけません。
指定したコミットに対するmain candidateの成功を公開workflowが確認した後、同じworkflowがtagを作成します。
tagの更新と削除も行いません。

== Release

release作業も通常の変更と同様に、短命なブランチとpull requestから開始します。

. 変更の互換性と利用者への影響からSemantic Versioningのバージョンを決め、管理対象componentを同期します。
+
[source,console]
----
node tools/sync-release-version.mjs --version X.Y.Z
----
+
このtoolはlink:release/version-sync.json[バージョン同期対象]に明示したmanifest、lockfile、公開仕様のfixtureおよび生成物だけを
更新します。更新前に部分的なバージョン変更を検出した場合は、ファイルを書き換えず停止します。
主要なmanifestのバージョンが揃っていることは``cargo make release-contract``が別に照合します。
. 差分を確認し、``release/notes.md``のRelease Notes、必要な仕様文書およびテスト用入力を更新してから、
  同期状態を検査します。
+
[source,console]
----
node tools/sync-release-version.mjs --check
----
. ``cargo make release-check``を実行し、pull requestの必須checkが成功したことを確認して``main``へ統合します。
. release対象のPull Requestをすべて統合し、公開対象が``main``の先端であることを確認します。
. その先端に対するmain candidateが成功してから、次のように公開workflowを実行します。
+
[source,console]
----
git fetch upstream main
candidate_sha="$(git rev-parse upstream/main)"
gh workflow run release-dispatch.yml \
  --ref main \
  -f product=lsp \
  -f candidate_sha="$candidate_sha"
----
. workflowが候補SHAとdispatch時点のmain先端の一致、同じSHAのcandidate成功、既存tagとReleaseの不在を検査し、
  同じrunでtagとGitHub Releaseを作成します。公開後、同じrunがLinux x86-64／ARM64のNixパッケージを
  buildし、runtime closureをbinary cache(``keishis.cachix.org``)へpushします。
. GitHub Releaseがstableとして公開され、予定されたassetだけを含むことを確認します。
. checksumとattestationを検証し、xref:#release-checklist[Release checklist]に従って受け入れ結果を記録します。

Release Notesの本文は``release/notes.md``に人が書きます。題名は``# AdocWeave <product> vX.Y.Z``とし、
``## 主な変更``、``## 対応環境``、``## 公開契約と破壊的変更``、``## vX.Y.Zへの移行``、
``## 更新とロールバック``、``## 既知の制約``、``## 配布物の検証``の7見出しをこの順に一度ずつ置いて、
各節に本文を書きます。選択した製品のversionと互換性判断に使うAPI世代は``tools/release-notes.mjs``が正本のfileから生成して
各節の後ろへ追記するため、本文には書きません。``cargo make release-contract``（``verify``に含む）がこの形を
検査し、公開workflowが同じtoolでGitHub Releaseの本文を生成します。

CLI引数、Language Server protocol、設定schemaなど、外部から利用する仕様を変更した場合は、変更内容と影響を
``## 公開契約と破壊的変更``へ記載します。利用者の作業が必要な場合は``## vX.Y.Zへの移行``へ操作を記載します。
前の版と比較していない仕様を「変更していません」と機械生成しません。

版を上げるときは、雛形``release/notes.template.md``を``release/notes.md``へ複製し、``X.Y.Z``を新しい版へ
置き換えてから各節を書きます。雛形の「記載してから公開」を含む案内文は、書き終えたら消します。残っている
場合は``release-contract``が未記入として拒否します。本文中の版表記は個数を問わず
``node tools/sync-release-version.mjs``がすべて置き換えるため、文面を変えても
``release/version-sync.json``を直す必要はありません。

公開処理の権限、candidateの再利用条件およびReleaseの状態遷移は
xref:docs/developer-guide/release-distribution.adoc[GitHub Releases配布仕様]を基準とします。
公開に失敗した場合は、再実行前にprivate draft、既存assetおよびattestationの対象digestを確認します。

公開後に問題が見つかった場合は、既存のtagやassetを置換せず、修正をpull requestで``main``へ統合して
新しいバージョンで最初から実行します。tag、assetまたはattestationの手動削除は監査可能な破壊的操作であるため、
実行前に対象、影響および理由を確認し、記録してください。

リポジトリの初期設定では``github-release`` Environmentを名前付きの権限・監査境界として作成し、
deployment branchを``main``だけに制限します。tag rulesetは使用しません。個人所有リポジトリでは
組み込みのGitHub Actions appをrulesetのbypass対象へ指定できず、bypassなしのrulesetは公開workflowの
tag作成も拒否するためです。tagを作成しない・付け替えないという規律は、<<tag,Tagの節>>の運用と
公開workflowの既存tag検査で守ります。この判断の背景は
xref:docs/developer-guide/adr/0006-direct-stable-releases.adoc[ADR 0006]を参照してください。

[#release-checklist]
== Release checklist

公開前の項目は各releaseで必ず確認します。いずれも機械が判定できるもので、失敗すれば公開できません。

公開後の項目は**任意**です。実際の画面操作や実環境での導入は人手でしか行えず、毎releaseで全経路を
確認すると一人では回らないためです。気になる経路を選んで確認し、結果は必要に応じてIssueへ記録します。
変更のなかった成果物は省略してかまいません。公開したassetそのものの完全性(checksum、attestation、
バージョン、binary cacheへの登録)は自動で確認できるため、任意の対象から外します。

公開後の手動確認を行う場合は、リポジトリのcheckoutやワークスペースの``target``を``PATH``へ含めない
clean環境で、公開assetだけを使って実行します。

=== 公開前

* [ ] ``flake.lock``で固定したRust stable、``toolchains.json``の``rustVersion``、rootワークスペースと
      Zed crateの``rust-version``が一致しています。
* [ ] 公開する製品のmanifestと製品内の生成物が同じ製品バージョンを持ち、ほかの製品の版を変更していません。
* [ ] ``release/notes.md``が公開する製品と版の内容になっており、題名と移行の見出しが
      ``versionSource``の値と一致しています（``cargo make release-contract``で検査します）。
* [ ] ``cargo make release-check``が成功しています。このtaskはClippy、文書、Zed、WASM、native／実WASM
      conformance、短時間fuzz、Web Worker、release fixture、WASM sizeおよび配布planを検査します。
* [ ] ``github-release`` Environmentが``main``だけを許可しています。workflowはこの外部設定を
      検査しないため、dispatch前にGitHubの設定画面で確認します。
* [ ] main向けのopen Pull Requestがなく、対象コミットが現在の``upstream/main``の先端であり、同じコミットの
      main candidateが成功しています。
* [ ] xref:docs/developer-guide/release-distribution.adoc[配布仕様]に定義したtarget、archive、metadataおよびasset集合が
      candidateと一致しています。

=== 公開後（任意）

次は人手でしか確認できない経路です。変更のあった成果物から選んで確認します。すべてを毎回行う必要は
ありません。問題が見つかった場合はIssueへ記録し、修正は新しいバージョンで公開します。

* [ ] VS Code拡張: Open VSXまたは公開VSIXから導入し、AsciiDoc認識、基本構文色付け、managed Language Serverの
      取得、更新、rollbackおよび削除を確認する。
* [ ] Zed拡張: 公開archiveとmanaged LSPをoverrideなしで使用し、AsciiDoc認識とLSP機能を確認する。
* [ ] browser package: cross-origin isolationを使わない環境で実WASMを読み込み、HTML、診断、projection、解析の取消しおよび
      取消し後の再解析を確認する。
